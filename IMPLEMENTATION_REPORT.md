Статус: этап 0 выполнен частично (см. ниже), **этапы 1–6 выполнены**, этап 7 выполнен частично (интеграционные проверки, выполненные по ходу).
Пометки: **[проверено]** — выполнено и наблюдалось; **[код]** — подтверждено чтением декомпилята/proto; **[не проверено]** — только предположение.

## Этап 0. Предпосылки

### Как связаны остановка, маршрут и направление [код]
- `stopService.proto`: `Stop{Id, Name map, Point{Latitude,Longitude}, repeated int64 Routes}`; комментарий разработчика: `Routes` — «список идентификаторов маршрутов, связанных с остановкой».
- `routeService.proto`: `Route{Id, TypeId, MainRouteId, Name map, repeated Direction}`; `Direction{Index, repeated Point Line, Duration, Distance, repeated StopPosition Stops}`; `StopPosition{StopId, LineIndex, OffsetDistance}`.
- Следовательно: остановка → `Stop.Routes` (id маршрутов); маршрут → `Directions[]`; направление, обслуживающее остановку, — то, в `Stops` которого есть этот `StopId`. Одна физическая остановка может числиться в нескольких направлениях одного маршрута.
- Тип транспорта: `Route.TypeId` = `routeType` в приложении; по `RoutesResourceHelper` 0 — автобус, 1 — троллейбус, 2 — метро, 3 — трамвай, 4 — микроавтобус. Строгого enum в коде нет, значения выведены из выбора иконок [вывод].

### Источник «всех маршрутов остановки» — подтверждённый способ [код, не запускалось]
1. Ближайшая остановка: Room-таблица `Stop` (`id`, `lat`, `lng`), доступна через `RouteComponent.getRouteDatabase()`. Полнота таблицы на устройстве **не проверена** (синхронизация через `StopService.list(updatedAfter)`).
2. Маршруты остановки: `StopService.get(stopId).Routes`, поскольку в Room `Stop.routes` не сохраняется. Локальная таблица `RouteDirectionStop` для этого **не годится**: она заполняется только для маршрутов, чьи детали уже загружались (`RouteRepository.getItem` грузит лениво, если строк <3).
3. Геометрия и направления: `RouteService.get(routeId)` отдаёт полный `Route` с `Directions[].Line` и `Stops[]` — то есть геометрию для ранее не открывавшихся маршрутов получить можно **[код]**; реальный запрос не выполнялся **[не проверено]**.

### Как обращаться к данным приложения из нового фрагмента [код]
- `OnayApp.get().getRouteComponent()` возвращает `RouteComponent` (может быть `null`, если город не выбран).
- `RouteComponent` отдаёт только `getConfigurationRepository()`, `getManagedChannel()`, `getRouteDatabase()` и методы `inject(...)` для конкретных классов. Геттеров `StopRepository`/`RouteRepository`/`PositionRepository` **нет**; добавить `inject(NearbyStopFragment)` значило бы править сгенерированный Dagger-код.
- `ManagedChannel` построен с `GrpcHeaderClientInterceptor`, который сам добавляет заголовки (в том числе `X-Auth-Token` из `GrpcTokens`). Поэтому рекомендованный способ: создавать gRPC-стабы (`StopServiceGrpc.newBlockingStub(channel)` и т.п.) на **существующем канале приложения**. Токены не извлекаются и не копируются, второго клиента нет.
- Для позиций автобусов: `PositionServiceGrpc` на том же канале (`PositionService.list(routes[])`), либо повтор существующего механизма — решить на этапе 5.

### Блокеры сборки нового кода [проверено]
- Есть: `javac` 27, `d8`, `zipalign`, `apksigner`, `adb`, `apktool`.
- Нет: `android.jar` (в `/opt/android-sdk` только `build-tools`, нет `platforms/`), `kotlinc`, инструмента dex→jar для classpath приложения (`enjarify` есть в `extra`).
- Решение (предлагается): писать новый код на **Java** (не требует Kotlin); `android.jar` — `platforms;android-36` через `sdkmanager` (пакет `android-sdk-cmdline-tools-latest` из AUR); classpath приложения — `enjarify` из `base.apk`/dex только для компиляции (классы приложения в итоговый dex не включаются).

## Этап 3. Реальные GPS и остановки [проверено на Poco X5 5G, Android 14]
- **Остановки** читаются из Room приложения: `OnayApp.get().getRouteComponent().getRouteDatabase().stopDao().getListRx()`, названия из `localizationDao().getList("Stop", id)` (язык по `Locale.getDefault()`, выбор в `StopNames`). На устройстве загрузилось 4021 остановка. Все обращения к базе идут в фоновом потоке, названия подгружаются только для показываемых остановок.
- **GPS**: используется существующий `kz.onay.ui.routes2.shared.MyLocationRequestHelper` (подключён как наблюдатель жизненного цикла, `getLocation()` читается опросом раз в 400 мс, таймаут 15 с). Его слушатель — вложенный интерфейс, недоступный по имени при компиляции, поэтому опрос. Перед ним: проверка разрешения (запрос через фрагмент) и включённости провайдеров. Свежесть и валидность координат: `LocationQuality` (макс. возраст 2 мин).
- **Ближайшая остановка**: `NearestStopFinder` (радиус 1 км, до 5 кандидатов), остановки разных сторон дороги не объединяются; рядом показываются кнопки других остановок не дальше чем на 120 м от ближайшей (`NearbyCandidates`).
- **Состояния**: загрузка; нет разрешения (с кнопкой «Разрешить», при «больше не спрашивать» открываются настройки приложения); геолокация выключена (кнопка «Включить», после возврата из настроек выполняется перепроверка); нет свежей координаты по таймауту; нет остановок рядом; пустая база; не выбран город. В последних четырёх случаях сразу открывается ручной выбор.
- **Ручной выбор**: на карте не более 80 ближайших к центру видимой области остановок, обновляются при остановке камеры.
- **Маршруты ещё не подключены** (этап 4): `AppDataSource` возвращает пустые списки, экран пишет «маршруты пока не подключены». Тестовые данные этапа 2 доступны через `--es data test`.
- Отладочные параметры отладочной Activity: `--es data test`, `--es state ...`, `--ed lat/--ed lng` (подмена координаты для проверок вне города).
- Проверено на устройстве: холодный запуск, загрузка 4021 остановки, фикс (точность 100 м), ближайшая остановка 173 м, соседние остановки как кнопки, режим ручного выбора на реальных данных, выбор остановки нажатием на маркер, состояние «геолокация выключена» с автоматическим ручным выбором, кнопка «Включить» открывает настройки, возврат запускает перепроверку.
- Найдено и исправлено по ходу: после возврата из настроек баннер ручного выбора оставался поверх найденной остановки (`start()` не сбрасывал режим выбора).
- **Не проверено на устройстве**: реальный отказ в разрешении (HyperOS не даёт отзывать разрешения через `adb pm revoke`, нужен ручной отзыв в настройках), устаревшая координата и таймаут (покрыты только JVM-тестами `LocationQuality`), пустая база и «город не выбран» (код есть, воспроизвести не удалось), поворот экрана и возврат из фона.
- Языковые замечания: названия берутся по языку устройства (на телефоне en-GB, поэтому английские); язык, выбранный в самом приложении, не читается (поле `languageManager` недоступно из внешнего кода).

## Этап 4. Реальные маршруты [проверено на Poco X5 5G, реальные данные]
- **Источник**: `StopService.Get(stopId).Routes` (id маршрутов остановки) и `RouteService.Get(routeId)` (название, тип, направления с остановками и линией). Вызовы идут по **существующему каналу приложения** (`RouteComponent.getManagedChannel()`), обычные блокирующие стабы с дедлайном 10 с. Результаты кэшируются на время процесса, повторный выбор остановки не повторяет запросы. Геометрия маршрутов ранее не открывавшихся маршрутов получена без участия старых экранов.
- **Что подтвердилось на устройстве**: `Stop.Routes` содержит id маршрутов; у каждого маршрута `RouteService.Get` отдаёт полные направления, остановки и линию (например 2 направления, 242–652 точки); запросы 16–881 мс; «неизвестное направление» в реальных данных не встретилось.
- **Авторизация (важно)**: канал приложения добавляет заголовок `X-Auth-Token` через `GrpcHeaderClientInterceptor`, но значение токена в нём не задано, пока его не передаст экран маршрутов. Родные экраны делают `grpcHeaderClientInterceptor.setShortToken(accountManager.getAccount().getShortToken())`; без этого вызов падает (`NullPointerException` в `Metadata.put`, наблюдалось). Новый экран повторяет ровно этот вызов приложения (`AppDataSource.applyAccountToken`): токен передаётся из аккаунта в перехватчик в памяти процесса, не читается, не пишется в лог и не показывается. Для этого экран получает сам перехватчик **рефлексией** по имени поля `provideInterceptorProvider` в сгенерированном Dagger-компоненте (в `RouteComponent` его нет). Это привязано к конкретной версии APK 3.6.5; при отсутствии поля выводится понятная ошибка. Если пользователь не вошёл в приложение, экран пишет «Войдите в приложение, чтобы видеть маршруты» (на устройстве не воспроизводилось: тестовый аккаунт был авторизован).
- **Компиляция**: у classpath нет `InnerClasses` и generic-сигнатур, поэтому вложенные protobuf/gRPC-классы названы через `$`, результаты builder'ов приводятся явно (подробнее в `docs/PATCHES.md`).
- **Названия и направления**: номер маршрута по языку (`RouteNames`), подпись направления «в сторону <последняя остановка направления>» (`DirectionLabel`, название из `Localization`). Показываются только направления, обслуживающие выбранную физическую остановку; если ни одно загруженное направление её не содержит, направление помечается неизвестным и рисуются все линии маршрута.
- **Экран**: остановка и заголовок показываются сразу, маршруты подгружаются в фоне («загружаем маршруты…»); ответ для уже сменённой остановки отбрасывается; частичные сбои считаются («не загрузилось: N»); при сбое остановки статус и кнопка «Повторить». Камера по умолчанию показывает окрестность остановки (±330 м), а не весь маршрут (линии тянутся через весь город); при выборе маршрута камера вмещает его целиком. Палитра цветов расширена до 12.
- Проверено на устройстве: остановка «Timiryazev st.», 3 маршрута (19, 56, 113) с реальной геометрией и стрелками направления; выбор 56 (подсветка, подпись «в сторону "Toimart" shopping center», остальные полупрозрачны); соседняя остановка (145 м) с другим набором маршрутов (19, 113); остановка с 15 маршрутами (троллейбусы 1, 9, 11 и автобусы) и подписью типа; выключенная сеть на остановке без кэша даёт «Не удалось загрузить маршруты остановки» и «Повторить», после включения сети повтор загружает 15 маршрутов.
- **Не проверено**: «не вошёл в приложение», частичный сбой отдельных маршрутов (`failed > 0`), поведение при истечении токена, поворот экрана и возврат из фона, одинаковые цвета при более чем 12 маршрутах, внешний вид экрана с 15 маршрутами после расширения палитры (телефон заблокировался до снимка), реальные транспортные позиции (этап 5).

### Дополнение к этапам 3–4: устаревшая координата на реальном устройстве
- Когда телефон долго простаивал, экран дважды дошёл до таймаута: в журнале `no usable fix: MISSING` и `no usable fix: STALE`. Старый helper приложения отдавал только давнюю координату сети и не получал свежую за 15 с; «Повторить» ничего не менял. Эти пути состояний подтверждены на устройстве.
- Исправление: при устаревшей координате пользователю предлагаются два действия: «Использовать его» (с возрастом координаты, `AgeText`, например «5 мин назад»; в подписи остановки появляется «(положение: …)») и «Повторить». Решение остаётся за пользователем, неточная координата не подставляется молча. Тесты `AgeTextTest` (5), 4 новых мутанта.
- Кнопка «Использовать его» на устройстве не нажималась: на последнем запуске свежая координата пришла сразу, поэтому состояние не воспроизвелось. Вёрстка двухкнопочной полосы проверена на состоянии «ошибка» (сообщение сверху, кнопка снизу).
- Внешний вид экрана с 15 маршрутами после расширения палитры до 12 цветов снимком не подтверждён.

## Этап 5. Транспорт в реальном времени [проверено на Poco X5 5G, реальные данные]
- **Источник**: `PositionService.List(routes[])` на том же канале приложения. Это конечный поток: последнее сообщение каждой единицы транспорта на перечисленных маршрутах. Родные экраны сохраняют его в свою таблицу Room `Position` и опрашивают раз в секунду; новый экран **ничего не пишет в эту таблицу** и не использует её, поэтому родные экраны не затрагиваются. Запросы только для маршрутов выбранной остановки и только пока экран виден.
- **Что подтвердилось на устройстве**: приходит `actualPoint` (широта, долгота, азимут, время), `routePoint` сервер не присылает (47 из 47 сообщений без него), поэтому используется `actualPoint`. Возраст отчётов 0–12 с; у всех единиц в одном ответе одинаковое время (это время снимка на сервере, а не время сообщения каждой единицы). Пример: 47 единиц на 3 маршрутах остановки, после фильтра по направлениям остановки на карте 25.
- **Фильтр** (`VehicleFilter`, чистая логика, тесты): только показанные маршруты; направление, обслуживающее остановку (если оно неизвестно, все); корректные координаты; отчёт не старше 3 минут; один последний отчёт на устройство; порядок по маршруту и устройству.
- **Отображение**: маркер-кружок цвета маршрута с номером и указателем направления движения (16 направлений, иконки кэшируются), маркеры обновляются на месте (перемещаются, добавляются, удаляются), а не пересоздаются; при выборе маршрута транспорт других маршрутов становится полупрозрачным. Строка статуса под подписью направления: «Транспорт на карте: N · обновлено ЧЧ:ММ:СС». После трёх неудач подряд: «Позиции транспорта недоступны, линии маршрутов показаны» (линии при этом остаются).
- **Опрос**: раз в 5 с; один запрос в полёте; опрос останавливается при уходе с экрана, при ручном выборе остановки и при смене остановки, возобновляется при возврате, не перезагружает остановки и маршруты.
- Проверено на устройстве: опрос раз в 5 с (журнал `vehicles on 3 routes: 47 ...`); маркеры на карте у остановки и на всём маршруте 56; выбор маршрута затемняет транспорт других; в фоне запросов нет (0 за 14 с), после возврата они возобновляются без перезагрузки остановок; тестовый режим данных работает.
- **Не проверено**: сбой отдельных запросов позиций (серия из трёх ошибок и сообщение), длительная работа (утечки, расход батареи), поведение при сотнях единиц транспорта, плавное перемещение между опросами (маркеры перепрыгивают).
- **Идея вне этапа**: показывать, какие единицы ещё едут к остановке, по `offsetDistance` (есть и в позиции, и в `StopPosition`); данных для этого хватает, но задачей не требовалось.
